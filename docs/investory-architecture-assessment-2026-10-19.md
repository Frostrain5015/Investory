# Investory 量化助手架构评估

评估日期：2026-10-19。代码位置：`D:/Java Projects/investory`，Maven 与前端声明版本均为 6.3.2。

本文依据本地源码、现有检查和官方技术资料。评估目标按“乙方为多个客户交付、A 股日线或分钟级规则策略、逐步开放有边界的自动交易”理解；未评估高频交易、交易所直连或大规模资管系统。建议与现状分开描述。本次没有修改 Investory 源码、连接券商账户或部署服务。

## 1. 决策结论

可以以 Investory 为基础开发，推荐渐进改造。账户、投资组合、持仓展示、盈亏、研究界面、对话交互和工具协议可以复用；真实订单管理、交易授权、风控、执行网关、成交对账属于需要新建的核心。

不建议为了接入 QMT 把整个项目重写成原生桌面程序。Web 同样属于客户端与服务端架构；浏览器还是桌面窗口，与服务部署在本机还是云端，是两个独立选择。当前 Electron 版本主要提供本地界面，仍默认请求云端业务 API。

面向多个客户的首选：React 统一前端 + Java 模块化业务服务 + 独立 Python 研究/回测 worker + 用户侧 Windows 交易网关。浏览器和 Electron 复用前端。完整本地部署作为有明确隐私需求客户的独立交付模式。

需要保留的运行边界：LLM 提议或解释，确定性程序判断既定规则；独立授权与风控决定是否可以执行；券商回报决定订单和成交事实。LLM 框架、MCP 两次调用和聊天界面的确认按钮都不能单独充当实盘授权系统。

## 3. 是否必须迁移桌面：四种部署形态

| 方案 | 放置方式 | 优点 | 代价和适用条件 |
|---|---|---|---|
| 云端 Web | 浏览器显示；业务、研究、模型在服务器 | 免安装、升级统一、多设备；最适合先做研究与信号 | 不满足数据完全不出客户环境；本身不能直接代替用户侧 MiniQMT |
| Web + 本地网关 | 界面/业务可在云；Windows 网关接用户券商终端 | 最少改动接入实盘；保留跨设备管理；交易凭据可留本地 | 网关必须安装维护；仍需明确哪些持仓、提示词和日志会上传云端 |
| Electron + 本地网关 | React 桌面窗口与独立网关在客户电脑；业务可云可本地 | 延续当前界面；便于托盘、通知、启动和诊断入口 | 安装包、签名、更新、杀毒兼容增加维护成本；套壳本身不带来隐私或稳定性保证 |
| 完整本地/内网部署 | UI、业务、研究、数据库、模型均在客户电脑或内网；网关在 Windows | 明确的数据边界；可脱离厂商云运行研究和授权内策略 | 环境、备份、算力和升级由客户侧承担；行情与交易仍依赖外部网络、券商服务 |

对当前项目：先选 Web + 本地网关，并保留已有 Electron。若首批合同明确要求全量本地，优先解决后端、数据库、身份认证、模型与日志的本地部署，而不是先换桌面 UI 框架。

另一个低成本私有模式是“本地浏览器 + 本地后端”，并不必须有 Electron。它能满足本地数据与本地模型需求，代价是安装和后台运行仍需独立管理。

### 哪些需求值得提供桌面端

1. 客户希望通过安装包完成配置、诊断、更新和日常启动。
2. 需要托盘、系统通知、文件导入、凭据库、模型与网关管理入口。
3. 以完全本地或内网模式交付，要求统一安装体验。

### 哪些问题桌面端不会自动解决

- 数据仍请求云端 API，就仍会进入云端；本地模型也不代表提示词、历史和日志不上传。
- 关闭界面不能决定策略是否继续执行；交易进程必须有独立生命周期和明确的停止行为。
- 休眠、断电、网络中断、券商退出仍会中断执行；不能承诺止损单始终能成交或急停能撤掉所有在途订单。
- 交易网关与 MiniQMT 的登录会话、自动启动、锁屏恢复须实测，不应假定券商客户端能直接作为无界面的 Windows 服务运行。

## 4. 改造前必须处理的代码问题

以下是局部源码审查和定向检查，不是全项目安全审计。

### 4.1 交易流水与真实委托必须分离

当前 POST `/api/transactions` 直接录入用户给定日期、价格、数量，再更新现金、持仓和净值。这适合资产记账。

实盘至少需要交易意图、授权策略、风险判断、委托、成交、账户快照与对账异常等独立实体。部分成交、拒单、撤单失败、提交超时后状态未知都应独立表达。真实成交通过来源标识投影到资产台账，不能让用户编辑记账记录反向篡改券商事实。

### 4.2 回测流没有按用户和任务隔离

[BacktestSessionManager](<D:/Java Projects/investory/backend/src/main/java/com/investory/crawler/BacktestSessionManager.java:12>) 使用全局 active、进度、日志和订阅者列表；[启动和订阅接口](<D:/Java Projects/investory/backend/src/main/java/com/investory/controller/api/BacktestApiController.java:98>) 没有将会话绑定到用户/任务。历史结果接口另有用户校验，这不等于运行中流已隔离。

面向多个客户交付前，应使用 user/account/job 归属校验，限制每用户并发，保证日志、事件重连和取消都定位到同一任务。

### 4.3 规则语义与成本需要校准

- [cross_above/cross_below](<D:/Java Projects/investory/script/backtest_helpers.py:340>) 目前只是大于/小于阈值，没有使用前一时点判断穿越。序列一直在阈值上方会持续返回 true。
- [简单模式卖出](<D:/Java Projects/investory/script/backtest_engine.py:323>) 直接把股数乘当前价格加回现金，未扣卖出手续费或卖出滑点；结束平仓同样如此。
- 默认 `commissionPct=0.008` 按小数费率相乘，即 0.8%；`slippagePct` 则除以 100。需要统一字段名称、单位和展示，不应把 0.008 误读成 0.008%。
- 以当前完整收盘价计算信号，再按同一收盘价成交，需要明确是否有可实现的执行假设；日线策略通常需选择后续可交易时点，并模拟未成交情况。
- A 股回测需按具体证券/板块维护交易日历、可卖数量、申报单位、涨跌停、停牌、除权除息、交易成本等规则，不能对所有品种写一个固定规则。

本次在内存中抽取实际函数，以合成行情执行：初始现金 10,000，10 元买入 500 股，次日同价卖出，费率 0.008、最低佣金 0、滑点 0，实际最后现金 9,960。若按当前相同费率双边收取，应为 9,920。此检查验证卖出佣金遗漏，不代表该假定费率适合真实账户。

### 4.4 自定义 Python 不是可信沙箱

[高级回测](<D:/Java Projects/investory/script/backtest_engine.py:473>) 通过字符串黑名单、定制 builtins 和 exec 执行用户代码，不能作为多客户不可信代码的安全边界；Windows 路径明确缺少 signal.alarm 保护。

[回测进程控制](<D:/Java Projects/investory/backend/src/main/java/com/investory/controller/api/BacktestApiController.java:132>) 先阻塞读取 stdout 到结束，再执行 15 分钟 waitFor，因而该 waitFor 不能覆盖前面的阻塞阶段。

优先开放经过验证的策略 DSL。保留任意 Python 时，应在独立低权限 worker 中限制 CPU、内存、时间、文件与网络访问；不挂载交易凭据。容器只是可选隔离组件，高威胁多租户还需更强沙箱或专用虚拟机。交易网关不要执行 LLM 生成的任意代码。

### 4.5 盘中数据的时间语义不充分

[研究服务缓存](<D:/Java Projects/investory/backend/src/main/python/stocksage_alpha/server.py:48>) 对 regime_status 等结果共用 4 小时 TTL，而 [Java 调度](<D:/Java Projects/investory/backend/src/main/java/com/investory/crawler/StocksageScheduler.java:119>) 每 30 分钟请求一次。合成时钟检查证实，30 分钟后仍命中原快照。请求频率不能证明分析结果已刷新。

[实时报价](<D:/Java Projects/investory/backend/src/main/java/com/investory/crawler/RealtimeQuoteService.java:90>) 给抓取结果标记接收时间；新浪解析只读取价格，未将源行情时间一并提取。应区分源事件时间、接收时间、计算时间和数据版本。交易风控必须拒绝过期或不完整数据，研究缓存与交易行情分开管理。

### 4.6 授权需要移到可信服务

[MCP 确认](<D:/Java Projects/investory/backend/src/main/java/com/investory/service/McpConfirmStore.java:49>) 把 token 返回给调用方，再允许其调用 confirm_action；这是一种两阶段写入协议，不能证明人已审批。当前还是内存暂存，重启后消失。

[聊天确认](<D:/Java Projects/investory/frontend/src/pages/ChatPanel.tsx:912>) 在前端发起写请求，并保存当前会话自动允许的操作类型。这可用于低影响记账交互，不能原样升级成实盘授权。

应持久化用户授权的账户、策略版本、标的范围、允许动作、单笔/累计限额、期限和撤销状态；需要手动确认时，由可信服务记录审批并绑定精确意图。网关执行前再次校验，不允许模型通过调用确认工具自行扩大权限。

### 4.7 本地交付、安全和迁移基础需要补齐

- [桌面 main.js](<D:/Java Projects/investory/desktop/main.js:18>) 全局设置 ignore-certificate-errors，需要在交易产品中移除并正确处理证书。已有 nodeIntegration=false、contextIsolation=true 是可以保留的基础。
- [AI 设置](<D:/Java Projects/investory/backend/src/main/java/com/investory/controller/api/AiSettingsController.java:204>) 将 API Key 原值写入数据库；应根据部署模式使用系统凭据库或应用加密与独立密钥管理。
- [本地模型代理判断](<D:/Java Projects/investory/script/ai_agent.py:2781>) 没有排除 loopback/内网地址；只有配置了代理才会影响实际请求。内存函数检查对本地地址返回需要代理。
- 标准迁移路径从 V2 开始，V2 假定 users 已存在，且并存非标准 migrations 目录与 DAO 启动 ALTER。需要补齐核心表基线并在空数据库上验证安装，不能仅依赖已有生产数据库。
- [Maven 前端构建](<D:/Java Projects/investory/backend/pom.xml:136>) 的 failonerror=false 可使前端构建错误不阻止后续流程；应让发布流水线对检查失败明确退出。
- Spring Boot 当前锁定 3.3.5；3.3.x 已结束开源支持，需规划升级到交付时仍受支持且经过回归验证的版本，而不是照抄旧文档中的目标版本。[官方说明](https://spring.io/blog/2025/06/19/spring-boot-3-3-13-available-now/)

## 5. 每层技术栈选择

### 5.1 展示与交互

| 选择 | 优点 | 代价 | 对本项目建议 |
|---|---|---|---|
| React + TypeScript + Vite | 当前已有组件、页面、类型和图表；Web/Electron 共用 | 大页面与请求状态需治理；不能仅靠类型断言验证 API 数据 | 保留；先引入清晰领域组件、运行时响应校验和统一错误处理 |
| Vue + TypeScript | 团队熟悉时开发顺畅，适合业务界面 | 重写现有 hooks、页面和组件，不能直接改善成交可靠性 | 仅在交付团队长期以 Vue 为主时考虑 |
| Qt/PySide 或 .NET 原生 UI | 与桌面功能集成直接，适合仅 Windows 的专用工作站 | 当前 React 资产大量重写；Web 版本需另建 | 不作为首版路线 |

图表可继续用现有 ECharts/Recharts，按“交易图表/普通统计图”封装适配层。服务端状态复杂后可引入 TanStack Query，少量客户端状态用 Context 或 Zustand；不必同时添加多套状态库。对话输出继续 SSE；行情/订单交互确有双向需求时再引入 WebSocket。

### 5.2 桌面容器

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| Electron | 当前已有；React、登录、更新逻辑可复用；统一 Chromium 行为 | 分发运行时带来资源和更新负担；需严格限制 IPC 与导航 | 当前迁移成本最低，先升级和加固 |
| Tauri 2 | 复用 React，采用系统 WebView，容器分发可更轻 | 引入 Rust、权限模型、插件与系统 WebView 兼容验证；Python/QMT/模型体积不会消失 | 客户确有安装包或资源指标后做实测原型 |
| 浏览器/PWA | 无桌面容器维护，升级快 | 对本地网关、后台进程和系统集成仍需另做安装组件 | 研究与信号产品的默认入口 |

[Tauri 架构](https://v2.tauri.app/concept/architecture/)；[Electron 安全文档](https://www.electronjs.org/docs/latest/tutorial/security)。容器资源节约须在同功能构建上测量，不能按宣传包体估算整个量化应用的占用。

### 5.3 业务服务和风控

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| Spring Boot 模块化单体 | 复用认证、事务、DAO、资产算法；适合订单状态、授权和审计 | JVM 与 Python 为双运行时；需治理 Controller 中的业务逻辑 | 首选。模块可分身份/组合/策略/信号/订单/风控/审计 |
| FastAPI 全 Python | 研究代码和接口同语言，原型快，类型校验便利 | Java 已有业务需要迁移；CPU 密集工作仍需独立进程，不能靠 async 自动加速 | 适合计算服务边界，不急于替换主后端 |
| Go 或 .NET | 可为独立网关提供强类型和进程管理 | 新语言和数据模型迁移；调用 MiniQMT 往往仍需 Python 桥接 | 有明确团队/运维收益后再引入 |

[FastAPI 多进程部署](https://fastapi.tiangolo.com/deployment/server-workers/)。语言不是账户隔离、幂等或风控正确性的替代品。日线/分钟级首版不需要为未测出的延迟瓶颈引入 C++。

### 5.4 策略和回测

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 自研规则 DSL + 共享指标/信号逻辑 | 贴合既定规则，容易版本化和审计；减少任意代码风险 | 需要自己验证撮合、成本、复权、账户约束 | 首选核心路径；不要照搬当前未校准的回测结果 |
| 事件驱动框架，如 VeighNa/vn.py | 有事件、策略、交易网关等框架资产 | A 股股票/ETF 的组合与执行规则仍需验证；不能假定已有插件适配任意券商版本 | 做一条策略和一个券商的适配试验，再决定引入范围 |
| VectorBT | 适合参数扫描、批量研究与快速试验 | 向量研究不替代真实委托生命周期；现行 Commons Clause 限制收费产品/服务的某些使用 | 商业授权和使用方式明确后作为研究工具 |
| RQAlpha | 提供可扩展的回测/交易框架 | 当前官方仓库明确仅限非商业使用，乙方交付需另行商业授权 | 不直接作为免费商用默认组件 |

[VeighNa 文档](https://www.vnpy.com/docs/cn/index.html)、[核心 MIT 许可](https://github.com/vnpy/vnpy/blob/master/LICENSE)；具体插件、数据源和依赖仍需分别核对。[VectorBT 许可](https://github.com/polakowo/vectorbt/blob/master/LICENSE.md)；[RQAlpha 官方声明](https://github.com/ricequant/rqalpha)。

回测与实盘尽量共享策略定义、指标计算、标的元数据和规则评估；历史撮合器与真实券商适配器必须分别实现。两者共享逻辑不代表历史成交假设天然真实。

### 5.5 行情与研究数据

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 现有公开源采集 | 接入成本低，已有研究功能可运行 | 接口、时效、字段和历史一致性需要检测；商用再分发权限不能从可下载推导 | 留作研究补充，不单独承担实盘唯一信号源 |
| 券商 xtdata | 与交易终端相邻，适合接入端行情和证券信息 | 权限、覆盖和下载范围依券商；研究数据版本仍需自管 | 实盘链路优先验证 |
| 正规授权历史/财务数据 | 可约定服务与商业使用范围，便于稳定研究 | 订阅、调用和再分发有成本和约束 | 根据客户策略所需字段选，不先购买全量高频数据 |

建立统一证券标识与来源映射，保留原始数据和处理版本，记录停牌/退市样本、公司行为、财报可知时间，处理缺失和异常。避免用未来可知信息构造历史信号。

### 5.6 存储与知识库

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| MySQL + Flyway | 当前业务和 Python SQL 已在使用，迁移最低 | 新交易表、索引、锁与事件日志需设计；现有 SQL 偏 MySQL 方言 | 首版业务主库继续保留 |
| PostgreSQL | 行级安全策略可增加多租户防线，可搭配 pgvector | Java/Python SQL、数据迁移、回归和运维都增加工作；RLS 配置不当或特权连接可绕过 | 有明确复杂查询/多租户/检索需求再迁移 |
| SQLite | 用户侧网关日志/断点存储无需安装数据库服务 | 写并发和多进程协调需设计；不替代云端多租户业务库 | 用于网关本地日志，集中一个写入方 |
| Parquet + DuckDB | 适合行情快照、批量分析、研究重现 | 不是订单事务主库；嵌入式模式的多进程并发规则需遵循 | 数据量和查询需求上来后增加，不是首版硬依赖 |

[PostgreSQL 行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)、[pgvector](https://github.com/pgvector/pgvector)、[DuckDB 并发说明](https://duckdb.org/docs/current/connect/concurrency)。

当前知识库是主题文章查找，用户记忆也不等于完整文档 RAG。首版策略规则用可版本化 JSON/DSL 与关系库保存；研报、笔记、公告才按需要进入全文/向量检索。研究文档应有用户归属、来源、日期、版本和引用位置。数值、仓位、委托与交易条件优先用结构化接口获取，不让向量检索决定资金事实。

### 5.7 智能体与模型

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 重构当前 Python Agent | 保留现有工具、DAG、业务语义和评测；依赖少 | 自己维护重试、恢复、会话状态和协议兼容 | 第一阶段先模块化，统一工具 schema、响应和错误 |
| LangGraph | 有图执行、检查点和人工介入相关基础能力 | 状态迁移和依赖升级有成本；检查点不会自动防止外部下单重复 | 工作流确实复杂且需要恢复时采用持久化存储 |
| 受控固定工作流 | 规则判断可重放、可审计，模型失败影响面小 | 灵活性低于开放式 Agent | 用于交易核心；开放研究对话在外层 |

[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)。不需要为首版增加多个自由协作智能体；它们不能替代明确的工具边界和授权。

推理服务独立部署：本地低并发可使用 llama.cpp；有合适 GPU、平台支持和并发需求时评估 vLLM；远程 API 作为用户明确选择的模式。保留兼容接口并按实际模型做工具调用、长上下文、引用、超时和失败评测，不以普通聊天流畅程度判断交易工具可靠性。

[llama.cpp 服务文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)、[vLLM 服务文档](https://docs.vllm.ai/en/latest/serving/online_serving/)。模型权重许可需另核对；本地模型不可用时继续确定性策略还是暂停，应由策略配置决定，不得静默改用云模型上传客户数据。

### 5.8 任务、消息与协议

| 选择 | 优点 | 代价 | 建议 |
|---|---|---|---|
| SQL 任务表 + 有租约的 worker + outbox | 可复用数据库，任务和待发事件随事务持久化；运维少 | 需实现领取、租约、幂等、超时和重试 | 首版适合；按账户串行化交易，回测可并行 |
| RabbitMQ / Redis Streams | 便于任务路由和消费者扩展 | 增加基础设施；确认/持久化/去重仍须正确配置 | 积压、吞吐和独立 worker 数量确有需要后再上 |
| Temporal | 适合跨服务、长时间、恢复和审批流程 | 独立服务和开发模型增加运维与学习成本 | 暂不作为少量客户首版必选 |

[Temporal 文档](https://docs.temporal.io/)。消息至少一次投递或工作流重放都不能证明券商只会收到一次订单。必须记录意图 ID、请求序号、券商委托号和成交号；状态未知时先查询和对账，不能盲目重下。

普通业务接口用 REST + 明确类型/错误码；单向进度保留 SSE。网关与云端可用主动发起的认证 TLS 长连接，必要时退化为带租约和有效期的拉取；不在用户电脑上暴露公网下单端口。gRPC 可作为后续内部协议选择，首版没有必要同时维护多套接口。

### 5.9 券商网关与交易授权

首选 Windows 原生 Python 进程 + 经券商确认版本的 MiniQMT/xtquant。xtquant 官方文档要求先运行 MiniQMT，并提供行情、委托、撤单、查询与回报相关接口。[官方快速开始](https://dict.thinktrader.net/nativeApi/start_now.html)

网关只接受有用户/账户归属、策略版本、有效期和防重标识的结构化指令；在本地独立检查授权、证券状态、行情年龄、可用资金/可卖数量和限额。输入不是任意 Python、自由文本或通用 shell 命令。

| 替代路线 | 适合情况 | 代价 |
|---|---|---|
| 券商 PTrade 等其他平台 | 客户券商只开放该平台，并明确支持所需交互模式 | 执行环境、协议和部署方式不同，需要独立适配与权限确认 |
| 券商正式机构接口 | 机构客户有相应账户、商务和技术支持 | 准入、协议、联调、运维成本更高 |
| 屏幕点击/模拟键鼠 | 不建议作为产品交易执行通道 | 依赖窗口、提示和界面布局，难以提供稳定的订单确认和状态恢复 |

统一定义 BrokerAdapter，包括连接、查询、提交、撤单、回报和重连对账；不同券商终端版本须分别联调。QMT 平台存在、外部 SDK 下单权限、第三方软件接入许可是三个独立条件。

程序化实盘还需按客户券商流程完成适用的报告和核查；上交所现行细则包括首次交易前报告以及软件名称、版本、开发主体等信息。[规则](https://www.sse.com.cn/lawandrules/sselawsrules2025/trade/universal/c/c_20250612_10781696.shtml)

### 5.10 部署、运维和可验证性

- 云端/内网主服务可先用容器编排文件统一 Java、数据库、Python worker 和配置；无需以 Kubernetes 作为首版前提。
- Windows 网关独立安装，锁定 Python/SDK 组合。不要把 Linux 容器化与 Windows 券商客户端运行混为一谈，也不要假设可以再分发券商安装包。
- 交易进程和 UI 独立；UI 升级不应自动中断执行。运行策略时的服务升级必须有停止接单、对账和恢复步骤。
- 为网关与业务 API 设计版本握手、兼容窗口、可回滚更新；新策略或模型版本不应直接替换在运行的授权版本。
- 日志使用关联 ID 串起数据版本、信号、风控、意图、委托和成交；记录原因和时间，不记录凭据；原始成交/审计记录与可过期研究缓存分开。
- 监控数据年龄、网关心跳、未确认委托、拒单/部分成交、对账差异、任务积压、模型错误与资源占用。告警要在用户能收到的渠道实际验证。
- 本地硬件需分别测模型推理、历史回测、行情处理和 UI 的资源竞争；GPU 内存够加载模型不代表多会话和长上下文都稳定。给研究任务限额，交易网关与风控不等待模型队列。
- 备份后要验证恢复，目标是重建策略配置与委托状态，并通过券商查询校验；不能只复制数据库文件就宣称可灾难恢复。

## 6. 推荐落地顺序与验收

| 阶段 | 主要改造 | 进入下一阶段的证据 |
|---|---|---|
| 基础校准 | 修复规则/成本、任务隔离、进程超时、空库迁移；拆分业务边界；依赖升级 | 可重复安装；规则黄金样例与费用用例通过；两个用户并发看不到彼此任务；超时任务能被终止 |
| 研究与信号 | 版本化 DSL、数据快照、确定性信号、通知与原因展示 | 相同策略/数据重放得到相同信号；过期数据不触发交易路径；信号可追溯 |
| 模拟执行 | Windows 网关、模拟 BrokerAdapter、订单状态机、账务投影 | 重复消息、重复回报、部分成交、拒单、乱序、重连和重启不造成重复记账或下单 |
| 手动确认实盘 | 客户券商准入、精确意图审批、限额、急停、对账 | 小范围账户验证实际回报与账务一致；超时后的未知状态不会盲重试；审批撤销可生效 |
| 有边界自动交易 | 固定策略版本、账户/标的范围、金额/频率限制、授权期限 | UI 关闭行为清晰；断网/重启恢复先对账；模型建议越界无法通过服务与网关校验 |

回测收益好不等于达到交易交付条件；模型输出合理也不等于策略有收益。策略研究有效性、软件正确性、券商执行可靠性应分别验收。

## 8. 最终选型建议

首版基线：React + TypeScript；Web 主入口，Electron 可选；Java/Spring Boot 模块化业务服务；MySQL/Flyway；独立 Python 研究与受控回测 worker；版本化 DSL；SQL 持久化任务与事件；用户侧 Windows/Python/MiniQMT 网关；网关本地 SQLite 日志；独立推理服务。

可延后决策：Vue 全面重写、Tauri 更换容器、主库迁移 PostgreSQL、引入完整量化框架、向量库、消息中间件、Temporal、Kubernetes、C++ 交易服务。应由真实的性能、隔离、交付或维护问题触发，而不是为技术栈齐全而引入。

对乙方而言，优先支出是券商联调、可靠数据、策略/订单模型、异常场景测试、客户侧安装升级和运维支持。当前没有客户规模、策略频率、历史数据规模和服务等级目标，因此不据代码行数承诺改造人日或预算。
